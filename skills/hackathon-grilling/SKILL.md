# 해커톤 요구사항 분석과 질문

과제 문서와 사용자가 전달한 실무자 답변을 근거로 문제를 이해한다. 행사 안내와 과제 지시가 우선이다. 사실, 확인되지 않은 가정, 제안을 구분하고 요구사항이나 측정값을 지어내지 않는다.

## 분석

1. README, 제공 데이터와 관련 코드에서 이미 확인할 수 있는 내용을 먼저 찾는다. 과제 목표, 사용자, 필수 결과물, 제약과 마감·제출 조건을 구분한다. 근거가 있는 파일이나 내용을 짧게 표시한다.
2. 빈칸 중 결과나 우선순위를 바꾸는 것부터 찾는다. 예를 들어 사용자와 실제 업무 흐름, 어떤 상황을 문제로 보는지, 성공 기준과 현재값, 데이터의 의미와 최신성, 예외 처리, 작업 범위와 보안 제약을 확인한다. 과제에 맞지 않는 항목은 생략한다.
3. 질문 사이의 선후 관계를 확인한다. 먼저 답이 필요한 질문과 그 답에 따라 달라질 후속 질문을 나눈다. 확인된 문서로 답할 수 있는 내용이나 사소한 구현 선택은 사용자에게 되묻지 않는다.
4. 실무자에게 보낼 질문을 우선순위 순으로 제안한다. 보통 당장 판단에 필요한 2~3개부터 짧게 제시하고, 왜 필요한지와 답에 따라 달라지는 결정을 한 줄로 설명한다. 필요하다면 선택지와 잠정 추천을 제시하되 실무자의 답으로 꾸미지 않는다. 더 많은 질문이 필수라면 누락하지 말고 묶어서 순차적으로 제시한다.

## 답변을 받은 뒤

- 업무 메신저 대화를 직접 볼 수 없으면 사용자가 전달한 답변만 반영한다. 실무자에게 직접 메시지를 보냈거나 확인받았다고 말하지 않는다.
- 답변과 과제 자료를 대조해 **확인된 요구사항 / 가정·미확인 / 다음 행동**을 갱신한다. 모순이 있으면 차이와 근거를 보여주고 필요한 질문을 제안한다.
- 확인된 범위에서 작고 검증 가능한 사용자 행동과 성공 기준을 정한다. 성공 기준의 수치가 확인되지 않았다면 측정 방법이나 확인 질문을 제안하고 수치를 만들어내지 않는다.
- 불확실한 사항이 핵심 목표나 데이터 보안에 영향을 주면 사용자에게 알리고 관련 결정을 확인한다. 그 외의 합리적인 구현 세부사항은 가정을 밝히고 진행하며, 답을 기다리는 동안 독립적으로 할 수 있는 작업은 계속한다.
- 과제에서 정한 문서가 있으면 그 형식을 우선한다. 없다면 기존 문서나 대화에 간결히 남긴다. 모든 결정에 대해 별도 승인, 새 문서, 이슈 트래커, 서브에이전트를 요구하지 않는다.

제출 전에는 실제 구현과 확인 결과를 바탕으로 결정 이유와 남은 한계를 설명할 수 있게 돕는다. 후속 서술형 중 AI 사용이 금지된 경우 이 스킬을 사용하지 않는다.

이 스킬은 [mattpocock/skills의 grilling](https://github.com/mattpocock/skills/tree/main/skills/productivity/grilling)에서 질문의 선후 관계를 정리하는 방식을 참고해 해커톤용으로 수정했다. 원본 저작권과 MIT 라이선스는 같은 폴더의 LICENSE에 있다.
